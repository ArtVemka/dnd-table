# Передача: проект «D&D Стол» (E:\DnD)

Этот файл нужен, чтобы продолжить работу в новом чате или после очистки контекста.
Прочитай его целиком — этого достаточно, чтобы понять суть. Устройство, протокол
событий и детали — в `README.md`.

## Что это

Портативное desktop-приложение на Electron для игры в **D&D 5e (2014)** по
локальной или виртуальной сети (Hamachi / Radmin VPN / ZeroTier / Porthole).
Один участник — ДМ: он поднимает стол (сервер в main-процессе Electron).
Остальные подключаются по адресу и попадают за общий стол.

**Жёсткое требование заказчика: приложение НЕ создаёт сеть и НЕ поднимает VPN.**
Оно только слушает порт в уже существующей сети и показывает адреса для
подключения. Не добавлять ничего, что «настраивает сеть за пользователя».

Состояние: **версия 0.9b собрана в exe и проверена.** Первый заход закрыл ТЗ,
второй — баги фишек и добавление сетки, рисования, настроек, списка листов у ДМ и
блока Porthole, третий — приближение карты, сворачиваемые панели, лист в
отдельном окне, починку холста и несколько карт на вкладку, четвёртый — стол без
сервера (проверка игры от лица игрока и заготовка листа, которая переезжает на
настоящий стол). Все автоматические проверки зелёные (`npm test` 84,
`npm run smoke` 169).

**Версия:** в `package.json` — `0.9.0-b` (строгий semver: с «0.9b»
electron-builder падает с «Invalid version»), а в интерфейсе показывается **0.9b**
(`app:config` отдаёт `versionLabel`). Артефакты называются
`D&D Стол Portable 0.9.0-b.exe`. Если заказчик попросит «ровно 0.9b» в имени
файла — это невозможно без правки имени вручную, объяснять это.

**Что заказчик сказал по языку:** пока оставляем только русский. Кнопка настроек
есть, выбор языка в ней — заглушка («переключатель появится, когда добавим
второй язык»). Настоящей локализации в коде нет: все строки в renderer и в
сообщениях сервера написаны по-русски.

## Как запускать, проверять, собирать

```bash
npm install

npm start                 # запустить приложение из исходников
npm test                  # 84 проверки сервера (роли, права, протокол, сетка, карты, кампании)
npm run smoke             # 169 проверок интерфейса в настоящем Electron
npm run dist              # собрать exe: однофайловый portable + dist/win-unpacked
npm run dist:portable     # собрать release/ + архив для отправки друзьям
npm run dist:verify       # проверить СОБРАННОЕ: asar, запуск exe, портативный режим
npm run dist:installer    # (необязательно) обычный установщик NSIS

node scripts/make-icon.js # перегенерировать build/icon.ico
```

Проверки запускают настоящее приложение. Чтобы окна не мелькали на экране,
используется переменная окружения `DND_HIDE_WINDOW=1` (или флаг `--hidden`) —
её читает `createWindow()` в `main.js`. **Заказчик не любит мелькающие окна —
этот режим сохранять.**

Если проверка где-то встала и непонятно где — `set DND_PROGRESS=1 && npm run smoke`
печатает шаги по мере выполнения (в тесте каждое название проверки уходит в
`console.log`, а smoke-тест показывает эти сообщения сразу).

## Архитектура: ключевые решения

1. **Рендерер всегда общается только с сервером** через Socket.IO. ДМ запускает
   сервер в своём main-процессе и подключается к нему же по `127.0.0.1`.
2. **Роль ДМ нельзя подделать:** сервер даёт роль `dm` только при одновременном
   loopback-подключении и предъявлении `hostKey` — случайного секрета, который
   main-процесс передаёт лишь своему окну через preload.
3. **Права проверяет сервер**, а не скрытие кнопок: игрок не может получить чужой
   лист, двигать/удалять чужую фишку, управлять картами и кампаниями.
4. **Связь клиента с персонажем — по локальному `playerId`** без пароля (так
   требует ТЗ про переподключение). Ключи в localStorage:
   `dnd-table.playerId`, `dnd-table.playerName`, `dnd-table.lastAddress`.
5. **Сервер — авторитетный источник состояния.** Клиент ничего не меняет у себя до
   подтверждения сервера.
6. **Загрузка изображений:** renderer читает файл через `FileReader` → base64
   data URL → событие Socket.IO → сервер проверяет MIME, размер и **сигнатуру
   файла**, кладёт файл в папку кампании и раздаёт по `GET /files/<имя>`.
7. **В состоянии хранится ОТНОСИТЕЛЬНЫЙ путь** (`/files/x.png`), потому что он
   попадает в кампанию и должен переживать смену порта. А окно открыто по
   `file://`, поэтому путь дополняется адресом стола функцией `assetUrl()` в
   `renderer/app.js` (обработчик `resolveUrl` у `MapView`). **Без этого браузер
   ищет файл в корне диска и картинки не показываются.**
8. **У ДМ всегда есть выбранная карта** (`viewedMap`), иначе кнопка «Загрузить
   изображение» отправила бы запрос без типа карты. Уже выбранную вкладку (даже
   пустую) не сбрасываем — так ДМ может загрузить и вторую карту.
9. **Кубик бросает сервер** (`crypto.randomInt`), `d1` всегда даёт 1, бросок
   рассылается всем и дополнительно объявляется в чате сервером — чтобы у тех,
   кто подключится позже, история чата совпадала.
10. **Автосохранение** раз в 60 секунд при изменениях, плюс при остановке стола и
    закрытии приложения.
11. **Портативный режим** в `resolveDataDir()` (`main.js`) — три случая:
    `PORTABLE_EXECUTABLE_DIR` (однофайловая сборка), файл-маркер `portable.txt`
    рядом с exe, иначе `app.getPath('userData')`.
12. **Три вкладки карт, в каждой — свой список:** `MAP_TYPES = ['world', 'battle',
    'sketch']` в `server/state.js` и в `renderer/dnd5e.js` (там же `MAP_LABELS`).
    Формат состояния: `maps[type] = {items: [{id, url, name, uploadedAt}], activeId}`.
    `uploadMap` добавляет карту к уже загруженным (а не заменяет!), `selectMap`
    выбирает, какую показывать, `deleteMap` удаляет одну по `mapId`.
    `normalizeMapSlot()` в `state.js` понимает и старый формат (`{url, name}`),
    поэтому кампании заказчика открываются — это проверено тестом «кампания
    старого формата открывается». Всё, что перебирает типы карт, обязано идти по
    `MAP_TYPES`, а не по жёсткому списку: так вкладки работают на сервере, в
    кампании и в списке сохранённых без отдельных веток кода.
    На клиенте карту вкладки достаёт `MapView.mapOf(type)` / `mapCount(type)` —
    не обращаться к `this.maps[type].url` напрямую, там теперь список.
13. **Сетка — свойство стола:** `room.grid = {enabled, cell}`, событие
    `setGrid` (только ДМ) и рассылка `gridUpdated`. Клетка равна размеру фишки,
    оба размера задаются одной CSS-переменной `--cell` на `.map-surface`,
    поэтому фишка ровно занимает клетку. Хранится в кампании.
14. **Ластик на холсте не портит подложку:** в редакторе два холста друг над
    другом — `--bg` (подложка) и `--draw` (штрихи, прозрачный). Ластик работает
    через `destination-out` по слою штрихов. Штрихи хранятся как список
    (`{tool, color, size, points[]}`), поэтому отмена — это просто `pop()` и
    перерисовка, без снимков пикселей.
15. **`GET /files/:name` отдаёт `Access-Control-Allow-Origin: *`.** Без этого
    холст с подложкой из загруженной карты считается «загрязнённым», и
    `canvas.toBlob()` не сохраняет рисунок. Удалять этот заголовок нельзя —
    проверка «подложка из карты не «загрязняет» холст» в
    `test/renderer-assertions.js` упадёт.
16. **Меню фишки закрывается только по клику ВНЕ меню.** Если снимать меню на
    `pointerdown` внутри него, пункты (и выбор файла) не срабатывают: элемент
    исчезает из документа раньше события `click`. Это был реальный баг
    заказчика, ловится проверками «нажатие внутри меню не закрывает его раньше
    времени» и «меню не мешает выбрать файл изображения».
17. **Подписи фишки задают свой `line-height`.** `.map-surface` сбрасывает
    `line-height: 0`, а `.token__label` обрезает лишнее через `overflow: hidden`.
    Без собственного `line-height` высота подписи равна только отступам (2 px) и
    имя фишки не видно вообще — тоже реальный баг заказчика.
18. **Приближение карты — это `transform` на `.map-surface`,** а не изменение
    размеров. Поэтому карта, сетка и фишки растут вместе, а размер клетки и
    фишек относительно карты не меняется (требование заказчика). `.map-surface`
    позиционируется абсолютно (`left/top: 50%` + `translate(-50%,-50%)`), вокруг
    центра стола — так и приближение «под курсором», и перетаскивание считаются
    от центра стола. Приближение никуда не отправляется: у каждого своё.
    Проверка «приближение — личное дело каждого: на сервер ничего не уходит»
    следит, чтобы в этот код не добавили emit.
19. **Отдельное окно листа** (`renderer/sheet-window.html` + `preload-sheet.js`)
    — это ещё один клиент того же стола: подключается тем же `playerId` (игрок)
    или с `hostKey` (ДМ, только просмотр). Контекст окна (адрес стола, hostKey,
    чей лист) хранится в main-процессе и выдаётся по случайному id из
    `additionalArguments`, а не через командную строку: сам секрет стола в
    аргументы не попадает. При остановке стола окна листов закрываются
    (`closeSheetWindows()`), поэтому проверять их надо во время работы —
    в `test/smoke-main.js` для этого стоит опрос окон параллельно с прогоном.
20. **`close()` у сервера стола сначала принудительно рвёт соединения**
    (`io.disconnectSockets(true)`) и только потом зовёт `io.close()`, плюс
    страховочный таймер на 5 секунд. Иначе остановка стола может зависнуть
    навсегда: если у участника оборвалась связь, у сокета остаются
    неотправленные данные, события `drain` не будет, и `io.close()` не вернётся.
    Именно так «Остановить стол» завис в проверках, когда окно листа закрылось
    резко. Это реальный сценарий (у игрока пропал Wi-Fi или упало приложение) —
    правку не откатывать.
21. **Стол без сервера — это подмена сокета, а не отдельный режим.** В
    `renderer/local-table.js` живёт `createLocalTable()`, который отдаёт объект с
    тем же набором методов, что Socket.IO (`on`, `emit`, `removeAllListeners`,
    `disconnect`), и повторяет правила `server/socket.js` (роль игрока, лимиты,
    обрезка текста, падение в `errorMessage` на неизвестное действие). Контроллер
    интерфейса о подмене не знает: в `connect()` достаточно `local: true`
    (`renderer/app.js`), поэтому весь остальной код — обработчики событий, панели,
    карта, лист — работает как с настоящим столом. **Если добавляется новое
    событие сервера, ему нужен обработчик и в `local-table.js`**, иначе в
    тренировке действие ответит ошибкой «В тренировочном столе это действие
    недоступно» (это тоже проверяется тестом).
22. **Тренировочный стол ходит в сеть не везде осознанно:** он не пишет файлы
    кампании (карты живут как data URL в памяти окна) и не сохраняет ничего,
    кроме листа персонажа. Лист хранится в localStorage под ключом
    `dnd-table.draftSheet.<playerId>` (функции `readDraft`/`saveDraft`), потому
    что заготовка должна дожить до подключения к настоящему столу.
23. **Заготовку листа предлагают отправить только на пустой лист.** Правило
    `shouldOfferDraft({draft, serverSheet})` (`renderer/local-table.js`) сверяет
    заготовку с тем, что лежит на столе у этого игрока: `sheetHasContent()`
    считает заполненным любой ручной ввод (имя персонажа, класс, характеристики,
    владения, заметки и т. д.), а лист, который сервер заводит новому игроку,
    отличается от пустого только именем игрока. Так заготовка физически не может
    затереть начатую игру. Вопрос задаётся в `offerDraftSheet()` при `joined`,
    когда роль — игрок.
24. **В тренировочном столе панель карты показывает игроку кнопки ДМ** (загрузка
    карты, сетка, удаление, список карт) — иначе карту для проверки взять негде.
    Это видно по `training` в контексте (`viewer()` в `renderer/app.js` →
    `MapView.render`), панель помечена «Проверка без сети:», а рисование карты и
    «Показать игрокам» остаются скрытыми: зрителей и прав ДМ тут нет. Сетка и
    размер клетки поэтому же доступны в настройках (`canManageGrid` там — это
    «ДМ или тренировка»), а не только ДМу. Форма создания фишки в панели фишек
    показывается ДМу и в тренировке, а обычному игроку — нет (раньше она была
    видна всем, и игрок получал отказ сервера).
25. **Лист тренировочного стола выносится в отдельное окно через общее
    хранилище.** Сервера, который свёл бы два окна, в этом режиме нет, поэтому
    каналом связи служит черновик листа в `localStorage`, а события `storage`
    работают как доставка: `LocalTable` подписывается на изменение своего ключа
    (`createLocalTable` → `onStorage`) и отдаёт правку как `characterSheetData`.
    Событие `storage` приходит только чужому окну — цикла «окно за окном» не
    бывает. **Замерено на настоящем Electron:** два окна приложения делят одно
    хранилище (`file://`), и событие из окна листа доходит до основного окна.
    В `main.js` окно листа открывается и без сервера (`openSheetWindow` принимает
    `training: true` и тогда кладёт в контекст пустой `url`), а `startHost()`
    сначала закрывает все окна листов: открытые в тренировке, они подключены не к
    столу, и правки в них разъехались бы с игрой.
26. **В проверках окно листа читается только после загрузки документа.**
    `webContents.executeJavaScript` по загружающемуся окну способен не вернуться
    вовсе и подвесить весь опрос, а лист окно подхватывает из черновика уже
    после загрузки. Поэтому опрос в `test/smoke-main.js` ждёт `did-finish-load`
    плюс паузу, страхуется таймаутом и различает окна по подписи связи
    (тренировка — «без сети»). Если проверки «отдельного окна листа» падают —
    смотреть сюда, а не в код окна.

## Уже реализовано (не переделывать без запроса)

Лист персонажа D&D 5e 2014 со всеми полями из ТЗ и автоматическим расчётом:
модификаторы `floor((значение − 10) / 2)`, бонус мастерства по уровню
(1–4 → +2 … 17–20 → +6), спасброски и 18 навыков с владением и компетентностью,
инициатива, пассивная Внимательность `10 + бонус Внимательности`. Бонус
мастерства можно задать вручную галочкой (для домашних правил).

Приватность листа: игрок видит и правит только свой. У ДМ во вкладке «Лист»
сначала **список игроков** (имя, статус «в сети/не в сети», кнопка «Открыть
лист →»); нажатие на имя открывает лист **в режиме просмотра**, кнопка
«← К списку игроков» возвращает назад. Если никого нет — «В лобби сейчас никого
нет». Раньше ДМ сразу видел пустой лист и выбирал игрока в выпадающем списке —
заказчик попросил заменить это списком.

Три вкладки карт (общая, локация/битва и рисунок), в каждой — свой список карт
с переключением стрелками «◀ ▶» и списком (загрузил новую — прежние остались),
фишки с координатами в долях 0..1 и картинками, кубики d1…d20, чат, список
участников с ролями и статусом, сохранение/загрузка кампаний с автосохранением.

Сетка на карте: включается кнопкой «Сетка» в панели карты или галочкой в
настройках, клетка ровно по размеру фишки, размер клетки — там же в настройках
(32/46/56/72/96 px). Видят все участники одинаково.

Рисование карты: кнопка «Нарисовать карту» / «Рисовать поверх карты» открывает
холст с кистью, линией, прямоугольником, ластиком, цветом, толщиной, отменой,
очисткой и привязкой начала и конца штриха к клеткам. Подложка выбирается списком
(чистый лист, любая из трёх карт, файл). «Сделать картой» сохраняет рисунок в
любую из трёх карт.

Окно «⚙ Настройки» на главном экране и на столе: версия (показывается 0.9b),
режим, папка данных (с кнопкой), язык (заглушка, только русский), а у ДМ за
столом — сетка и размер клетки. Панель «Адреса для подключения» сворачивается
кнопкой и в свёрнутом виде показывает основной адрес; в ней же отдельный блок
Porthole с адресом `http://127.0.0.1:<порт>` и кнопкой «Открыть Porthole в Steam».

Приближение карты у каждого своё: кнопки «−/+» и «⤢» сброс в углу карты, колесо
мыши (к ближайшей точке) и перетаскивание карты мышью. Карта, сетка и фишки
увеличиваются вместе; на других участников это не влияет.

Сворачиваемые панели: «◀ Участники» убирает левую панель целиком, «Панель ▸»
сворачивает правую до иконок вкладок (клик по иконке разворачивает обратно).
Выбор помнится в localStorage (`dnd-table.leftPanelCollapsed`,
`dnd-table.rightPanelCollapsed`).

Лист персонажа можно вынести в отдельное окно («⧉ Отдельным окном»): игрок — свой
(правится), ДМ — лист выбранного игрока (только просмотр). После выноса панель
стола сворачивается до иконок. Окна листов закрываются вместе со столом.

Холст: подложка выбирается списком (чистый лист, любая загруженная карта, файл),
размер холста всегда кратен клетке, подложка не растягивается, сетка холста
тусклая и тонкая (её не спутать с сеткой стола). На пустой вкладке холст сам
берёт карту, показанную игрокам, — раньше ДМ начинал с пустого листа и думал,
что «карты не видно».

**Стол без сервера** (кнопка «▷ Запустить стол без сервера (как игрок)» в
настройках, она видна только вне стола): открывается обычный экран стола, но
сервер не поднимается вообще. Работают лист персонажа (сохраняется в localStorage
и переживает перезапуск), кубики, чат, вкладки карт с загрузкой карты для
проверки, сетка и своя фишка (в тренировке она сразу назначается игроку). Лист
выносится в отдельное окно так же, как за столом, только берётся из общей
заготовки. В шапке вместо «подключён» написано «проверка без сети», бейдж связи —
«без сети», в панели карты стоит пометка «Проверка без сети:». При подключении к
настоящему столу заготовка листа предлагается к отправке, если на столе для этого
игрока лист ещё пуст (см. пункт 23 архитектуры).

## Лимиты

| Что | Значение | Где |
| --- | --- | --- |
| Форматы изображений | только PNG, JPG, WEBP | `sniffImageFormat()` в `server/socket.js` |
| Размер изображения | ≤ 10 МБ | `LIMITS.maxImageBytes` |
| Имя | ≤ 40 символов | `LIMITS.maxNameLength` |
| Сообщение чата | ≤ 1000 символов | `LIMITS.maxChatLength` |
| Характеристики | 1..30, уровень 1..20 | `server/state.js` |
| Фишек на столе | ≤ 200 | `LIMITS.maxTokens` |
| Карт в одной вкладке | ≤ 20 | `LIMITS.maxMapsPerType` |
| Размер клетки сетки | 24..120 px (по умолчанию 46) | `GRID` в `server/state.js` |
| Холст рисунка | большая сторона до 1600 px, кратно клетке (не меньше 8 клеток) | `SKETCH` в `renderer/dnd5e.js`, `SKETCH_CELLS` в `renderer/table.js` |
| Приближение карты | 0.5x … 6x, шаг кнопки 1.25 | `ZOOM_*` в `renderer/table.js` |
| Порт | перебор от 32100 (128 попыток), иначе выдаёт ОС | `pickPreferredPort()` в `main.js` |

## Что нельзя ломать

* **`release/D&D Стол/data/campaigns` — это РЕАЛЬНЫЕ кампании заказчика.**
  `scripts/make-portable.js` копирует файлы поверх и не очищает `data`; архив
  для друзей собирается **без** кампаний ДМ. Не возвращать `rmSync(releaseApp)`.
* **`build.files` в `package.json`** исключает `test/`, `dist/`, `release/`,
  `build/`, `.qwen/`, `*.md`, `*.zip`, `*.log`, `*.txt`. Однажды папка `release/`
  не была исключена — `app.asar` раздулся с 3.5 МБ до 526 МБ, а portable-exe с
  96 МБ до 342 МБ. `dist:verify` теперь это ловит (размер пакета и отсутствие
  лишних папок). Исключение `*.txt` появилось после того, как в пакет попали
  логи проверок (`smoke-final.txt`, `dist-build.txt`) — не убирать.
* **Если собранное приложение падает сразу при запуске** (exe завершается с
  кодом 1 и без единого сообщения), почти всегда виновата частично
  перезаписанная папка `dist/win-unpacked`: Windows не отдала файлы убитому
  процессу из прошлого прогона. Лечится удалением папки и полной пересборкой:
  `rmdir /s /q dist\win-unpacked && npm run dist`. Проверить запуск можно так:
  запустить exe с `--remote-debugging-port=9345` и открыть
  `http://127.0.0.1:9345/json/list` — у рабочей сборки там есть цель
  `.../renderer/index.html`, у сломанной список пуст.
* **`res.sendFile(...)` с колбэком** в `server/socket.js`: без колбэка Express
  печатает стек в консоль на каждый отсутствующий файл.
* **`Access-Control-Allow-Origin: *` на `/files/:name`** — см. пункт 15: без него
  не работает сохранение нарисованной карты.
* **Меню фишки и `line-height` подписи** — см. пункты 16 и 17: это починенные
  баги заказчика, на них есть проверки.
* **`io.disconnectSockets(true)` перед `io.close()`** — см. пункт 20: без этого
  «Остановить стол» может зависнуть навсегда при оборванной связи у участника.
* **`assetUrl`/`resolveUrl`** — см. пункт 7 выше.
* **События тренировочного стола** (`renderer/local-table.js`) должны совпадать с
  серверными: добавили событие в `server/socket.js` — добавьте обработчик и туда
  (пункт 21), иначе в режиме без сервера действие будет отвечать ошибкой.
* **`shouldOfferDraft` из `renderer/local-table.js`** — см. пункт 23: заготовка
  листа не должна затирать лист, который игрок уже начал заполнять за столом.
  Проверки «заготовку предлагают только когда на столе лист ещё пуст» и «при
  подключении к столу предлагают перенести заготовку листа» это стерегут.
* **Ключ и формат черновика листа** (`dnd-table.draftSheet.<playerId>`) — см.
  пункт 25: это единственный канал между основным окном и отдельным окном листа
  в тренировочном столе. Переименование ключа или смена вида сохранённого листа
  разведёт окна, а проверка «правки в отдельном окне листа доходят до
  тренировочного стола» этого не заметит (она подставляет событие вручную).
* **`process.exit()` съедает буфер stdout** при выводе в пайп, поэтому в
  `test/packaged-smoke.js` используется `finish(code)` с короткой паузой перед
  выходом. Иначе отчёт теряется и падение выглядит «немым».

## Известные ограничения и открытые вопросы

* **Внешний вид заказчик ещё не оценивал.** Все проверки смотрят на структуру и
  поведение, но не на то, как это выглядит. Не утверждать, что «красиво/удобно» —
  спрашивать.
* **Языка два нет, и это решение заказчика** («пока только русский»). В настройках
  стоит неактивный список «Русский» с пояснением — это заглушка под будущий
  переключатель, а не забытая функция. Если заказчик захочет второй язык, это
  большая работа: строки разбросаны по всем файлам `renderer/` и по сообщениям
  сервера в `server/socket.js` и `server/state.js`.
* **Porthole не создаёт виртуальный адаптер** (он прокидывает порт через Steam,
  у игрока порт открывается локально), поэтому в списке адресов его нет —
  вместо этого есть отдельный блок с адресом `127.0.0.1:<порт>`. В
  `classifyAddress()` есть распознавание адаптера с именем «Porthole» на случай,
  если он всё-таки появится.
* **Открытый вопрос от заказчика закрыт:** «загружать другую фотографию карты, а
  не заменять текущую» — во вкладке теперь список карт: «Загрузить ещё карту»
  добавляет, «◀ ▶» и список переключают, «Удалить карту» убирает только выбранную.
  Три вкладки остались как были (так и просил).
* **Тренировочный стол ничего не пишет на диск, кроме листа.** Карты, фишки и чат
  там живут в памяти окна и исчезают при перезапуске — это осознанное решение
  (режим для проверки, а не для игры), оговорено в README. Если заказчик захочет
  сохранять и тренировочные карты, придётся завести для них хранилище.
* **В тренировочном столе нет ДМа**, поэтому назначение фишек недоступно, а своя
  фишка создаётся сразу своей; «Показать игрокам» и рисование карты скрыты.
  Попытка сделать недоступное действие возвращает понятную ошибку в тост.
* Доверенная сеть: у игрока нет пароля, привязка к персонажу — по `playerId`.
  Осознанно, оговорено в README.
* Форматы строго PNG/JPG/WEBP (по ТЗ). GIF/BMP/HEIC отклоняются с сообщением,
  называющим реальный формат.
* Цель `nsis` (`npm run dist:installer`) собиралась успешно, но после смены
  конфига заново не перепроверялась — установщик не основной путь.
* Незакрытая мелочь: сразу после `npm run dist:verify` сборка `npm run dist` может
  упасть с `EBUSY: rmdir 'dist\win-unpacked'`, потому что Windows не успевает
  освободить дескрипторы убитого процесса. Лечится повтором.
* Тот же класс проблем у архива: свежескопированный `release/…/D&D Стол.exe`
  первое время держат Windows и антивирус, и `Compress-Archive` падает с «used by
  another process». `scripts/make-portable.js` поэтому делает до трёх попыток с
  паузой 5 секунд. Там же обязателен `-ErrorAction Stop`: без него PowerShell
  печатает ошибку, но возвращает код 0, и сборка отдаёт молча испорченный архив
  (именно так и было один раз).

## Как работать с заказчиком

Пишет по-русски, коротко и по делу, ставит задачи исчерпывающими ТЗ и ожидает,
что объём будет закрыт сразу, а не частями. Решения по функциональности и
интерфейсу принимает сам; инструментальную часть (сборка, окружение, запуск
проверок) делегирует. Ожидает, что ассистент реально запускает сборку и проверки
и докладывает результат, а не выдаёт команды.
