# Design

## Context

См. `proposal.md`. Ниже только то, что влияет на устройство.

* Main-процесс Electron владеет сервером, кампанией и окнами, но не знает роль
  участника, состав комнаты и имя персонажа. Это знает renderer (`app.role`,
  `app.room`, `app.room.sheets`).
* Настройки интерфейса лежат в `localStorage` renderer, у main своего хранилища
  настроек нет. Значения по умолчанию задаёт renderer.
* `build.files` перечисляет корневые файлы поимённо. Новый модуль в корне без
  правки списка не попадёт в portable-сборку.
* Android собирает тот же renderer, но без Electron. Мост выставляет
  `desktop.isAndroid = true`.
* Discord Rich Presence работает только через локальный канал запущенного
  клиента: именованный канал на Windows, unix-сокет на Linux. Сетевого API для
  присутствия нет. Нужен зарегистрированный Application ID и ассеты, секретов
  нет.

## Goals / Non-Goals

**Goals:**

* Один необязательный канал наружу, который не может изменить состояние стола.
* Ноль новых runtime-зависимостей и ноль сетевых запросов.
* Ошибки Discord не видны игроку и не задерживают запуск.
* Проверяемая логика кадров и текста активности без живого Discord.

**Non-Goals:**

* Кнопка «Присоединиться», join secret, бот, OAuth, голосовой канал.
* Присутствие на Android и синхронизация настройки между компьютерами.
* Свои картинки кампании в ассетах: Discord принимает только заранее
  загруженные ключи.

## Decisions

### 1. Renderer присылает состояние, main собирает текст

Renderer отправляет только `{enabled, mode, campaignName, characterName,
playerName, playerCount}` через `presence:update`. Main проверяет типы, режет
строки, убирает управляющие символы и сам подставляет шаблоны «Мастерит …»,
«Играет: …». Альтернатива, где renderer присылает готовые `details`/`state`,
отклонена: тогда любая ошибка или чужая правка renderer может вынести в Discord
что угодно, а требования к составу активности держатся только на честности
вызывающего.

### 2. Свой тонкий клиент вместо библиотеки

Нужна одна команда `SET_ACTIVITY`. Пишем `discord-presence.js` на `net`:
рукопожатие, кадры `opcode + uint32 length + JSON`, ответ на PING, повторное
подключение. Альтернативы: `@xhayper/discord-rpc` тянет `@discordjs/rest` ради
OAuth и голоса, старый `discord-rpc` архивный и требует GitHub-пакет
`register-scheme`. Обе добавляют больше кода, чем заменяют.

Пути: Windows `\\?\pipe\discord-ipc-0..9`; Linux `$XDG_RUNTIME_DIR`, затем
`TMPDIR/TMP/TEMP`, затем `snap.discord` и
`app/com.discordapp.Discord*`, `app/dev.vencord.Vesktop`. Перебираем индексы
0..9 и замолкаем, если ни один не открылся.

### 3. Main владеет соединением и временем

Renderer вызывает `syncPresence()` после `joined`, в обработчике `disconnect`,
при уходе на главный экран и при смене имени персонажа. Main сравнивает новое
состояние с уже отправленным и не шлёт повтор, а выключение снимает активность
сразу. `startedAt` живёт, пока режим не сменился на неактивный. Настройка
`enabled` приходит в каждом вызове, поэтому отдельного канала для тумблера не
нужно.

### 4. Выключение снимает активность, но не рвёт соединение

При `enabled: false`, главном экране, тренировке и отключении отправляется
`SET_ACTIVITY` с `activity: null`. Сокет остаётся открытым до выхода из
приложения: включение обратно срабатывает сразу. При выходе сокет закрывается,
Discord сам убирает активность.

### 5. Недоступный Discord это норма

Нет клиента, нет канала, отказ в рукопожатии, закрытие сокета: ошибка уходит в
отладочный лог (только при `DND_DEBUG_PRESENCE=1`), пользователю ничего не
показывается. Повтор с задержкой 5, 10, 20, 40, 60 секунд, дальше 60. Таймер
повтора `unref()`, чтобы не держать процесс. Любое новое состояние сначала
ставится в очередь, поэтому после подключения уходит актуальное, а не старое.

### 6. Текст и границы

`details` и `state` режутся до 128 символов, имена до 64, переводы строк и
управляющие символы заменяются пробелом. Пустая кампания даёт «Ведёт стол»,
пустой персонаж даёт имя участника, пустое имя участника даёт «Игрок».
Активность всегда `instance: false`, таймер в миллисекундах эпохи. Никаких
полей из карты, чата, журнала и никаких идентификаторов.

### 7. Ассеты и Application ID

Application ID и ключи `app_icon`, `d20` лежат константами в модуле. ID
публичный. Если он пустой, модуль сразу выключен: так живут тесты и форки.
Название игры в Discord: `D&D Table`, задаётся при регистрации приложения и
кодом не меняется.
Картинки: `build/icon.png` 512 px и отдельная d20, обе загружаются вручную в
кабинет Discord.

### 8. Настройка и платформа

Тумблер живёт в «Настройки» → «Общие», ключ
`dnd-table.discordPresence` в `localStorage`, значение по умолчанию `false`.
Под тумблером подпись про друзей и общие серверы. На Android
(`desktop.isAndroid`) блок не рисуется, IPC не вызывается. В `preload.js`
добавляется один метод `setPresence`, без доступа к `ipcRenderer` из renderer.

### 9. Сборка и проверки

`discord-presence.js` добавляется в `build.files`. `packaged-smoke` проверяет,
что файл есть в `app.asar` и что без Discord приложение стартует. Модульные
тесты в `test/presence.js`: сборка кадров, разбор склеенных и разрезанных
кадров, тексты для мастера и игрока, обрезка строк, ответ на PING. Живой Discord
в CI не нужен; ручная проверка на Windows и Linux остаётся.

## Risks / Trade-offs

* Протокол неофициальный → один адаптер, молчаливое отключение, ручная проверка
  после обновлений Discord. Если формат сменится, игра не пострадает.
* Discord запущен от администратора, приложение нет → канал недоступен.
  Признаём это, ошибку не показываем.
* Flatpak и snap на Linux здесь негде проверить → покрываем известные каталоги,
  проверяем на обычной установке, риск фиксируем в release notes.
* Имя кампании и персонажа видны друзьям → включение только вручную, подпись
  рядом с тумблером, никаких других данных.
* Две копии приложения на одном компьютере (мастер и игрок для теста) →
  активность перебивает друг друга, побеждает последняя. Считаем допустимым.
* Application ID зашит в код → форкам нужно заменить константу и загрузить свои
  ассеты; это описано в README.

## Migration Plan

Данные не мигрируют: формат кампании не меняется. Выкатываем сразу выключенным,
включаем только на своём компьютере. Откат: убрать тумблер и модуль, ничего в
кампаниях не чистить. Для релиза нужен один ручной шаг: зарегистрировать
приложение Discord и загрузить ассеты.
