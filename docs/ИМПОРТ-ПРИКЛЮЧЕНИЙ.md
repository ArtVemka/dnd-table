# Импорт внешних приключений — техническое задание

Статус: черновик для согласования. Версия 1 документа.

## 1. Назначение и границы

ДМ получает возможность загрузить внешнее приключение (пока только Foundry VTT),
посмотреть, что внутри, выбрать нужное и встроить это в кампанию.

**Вне границ:** редактирование чужих систем правил, синхронизация с Foundry в обе
стороны, автозагрузка модулей Foundry, выполнение их кода, продажа и публикация
импортированного контента.

## 2. Пайплайн

```
источник → адаптер → нормализация → валидация → предпросмотр
         → выбор пользователя → маппинг в модель D&D Стола
         → сохранение в кампанию → отчёт
```

Каждый шаг — отдельная чистая функция. Любой шаг может прервать конвейер,
сообщив причину; конвейер не имеет побочных эффектов до шага сохранения.

## 3. Раскладка модулей

```
server/importer/
├── core/
│   ├── pipeline.js      прогон шагов, сбор ошибок, никакого ввода-вывода
│   ├── normalize.js     внешняя сущность → внутренняя модель
│   ├── validate.js      проверки внутренней модели
│   ├── preview.js       сводка для предпросмотра
│   ├── map.js           внутренняя модель → модель кампании
│   └── report.js        итоговый отчёт
├── adapters/
│   └── foundry/
│       ├── index.js      canHandle / inspect / import
│       ├── json.js       Adventure JSON, отдельные документы
│       ├── zip.js        модуль/мир: module.json + packs/
│       └── leveldb.js    чтение compendium-паков
└── errors.js            типизированные ошибки конвейера
```

**Ядро не зависит ни от Electron, ни от файловой системы.** Оно получает уже
прочитанные данные (`Buffer`/`string`/объект) на вход и возвращает структуры на
выход. Всё, что связано с диском, — в адаптерах.

В main-процессе остаётся только IPC-обвязка и файловые операции: показать диалог
выбора файла, прочитать выбранный путь, записать результат в кампанию.

## 4. Контракты

Типы описываются в JSDoc — проект без TypeScript, а типы нужны для
самодокументирования.

```js
/**
 * @typedef {Object} ImportInput
 * @property {string} [path]       путь к файлу, если источник локальный
 * @property {Buffer} [data]       содержимое файла
 * @property {string} [url]        адрес для сетевого источника
 * @property {Object} [options]    параметры источника
 */

/**
 * @typedef {Object} ExternalEntity
 * @property {'scene'|'actor'|'item'|'journal'|'rolltable'|'macro'} kind
 * @property {string} sourceId
 * @property {string} name
 * @property {string[]} [tags]
 * @property {{data: string, mime: string, bytes: number}} [image]  data URL
 * @property {ExternalEntity[]} [children]
 * @property {Object} [raw]        исходные данные источника, без нормализации
 */

/**
 * @typedef {Object} ImportPreview
 * @property {string} sourceId
 * @property {string} sourceTitle
 * @property {ExternalEntity[]} entities
 * @property {Object} [warnings]
 */

/**
 * @typedef {Object} ImportOptions
 * @property {string[]} include    sourceId выбранных сущностей
 * @property {Object}   [mapSlots]  куда класть сцены
 */

/**
 * @typedef {Object} ImportResult
 * @property {Object} patch        изменения к кампании
 * @property {ImportReport} report
 */

/**
 * @typedef {Object} Adapter
 * @property {string} id
 * @property {(input: ImportInput) => boolean} canHandle
 * @property {(input: ImportInput) => Promise<ImportPreview>} inspect
 * @property {(input: ImportInput, options: ImportOptions) => Promise<ImportResult>} import
 */
```

## 5. Адаптер Foundry

### Входы, по которым выбирается источник

| Вход | Признак | Файл-адаптер |
|---|---|---|
| JSON-экспорт Adventure | распознан признак adventure в корне | `json.js` |
| Отдельный документ | один объект известного типа | `json.js` |
| ZIP модуля/мира | есть `module.json` либо `packs/` | `zip.js` |
| Compendium-пак | расширение `.db` либо содержимое LevelDB | `leveldb.js` |
| Manifest по URL | запрошен URL | `manifest.js` + `zip.js` |

`canHandle` обязан работать **без** полного разбора файла: достаточно первых
 kilobайт для JSON, центрального каталога для ZIP. Полный разбор — в `inspect`.

### Про порядок источников

Приоритет: явный URL → JSON-документ → ZIP → `.db`. Пересекаться не должны,
но при совпадении побеждает более специфичный.

### Compendium-паки

Формат — NeDB поверх LevelDB. Чтение идёт через `classic-level`.

**Установлено проверкой:** пакет ставится в проект без пересборки —
`classic-level@3.0.0` распространяется через N-API-prebuilds, и в Electron 28
(ABI 119) загружается и пишет данные. Ограничение: prebuilds есть не для всех
платформ — нет `linux-arm64` на glibc и `win32-arm64`. Сборка под эти платформы
не проверена и должна быть объявлена неподдерживаемой, пока не появится
подтверждение.

Ключи в NeDB — это JSON-строки вида `!<base64 строки>`. Значения хранятся
раздельно, поэтому нужен обход по всему диапазону базы, а не точечные `get()`.

## 6. Нормализация

Приводит содержимое источника к `ExternalEntity[]`. Правила:

- изображение принимается только `png`, `jpeg`, `webp`;
- каждый байт проверяется по сигнатуре, а не по расширению или MIME;
- размер ограничен теми же 10 МБ, что и загрузка карт в игре;
- всё, что не распознано, остаётся в `raw` и попадает в отчёт как «пропущено»;
- `macro` нормализуется, но **никогда не выполняется** — в том числе при
  импорте `rolltable`, где макросы часто используются как результаты.

## 7. Валидация

Проверки уровня кампании, а не источника:

- имена — через существующий `sanitizeText`, с теми же лимитами длины;
- количество сущностей — не выше предела кампании;
- суммарный объём изображений — в пределах разумного, с отчётом при превышении.

## 8. Предпросмотр и выбор

Предпросмотр показывает: название источника, число сущностей по типам,
перечень с пометками о том, что не распознано и что будет потеряно при
маппинге. Пользователь выбирает галочками; выбор хранится как `include: sourceId[]`.

## 9. Маппинг в модель D&D Стола

Здесь главная проблема задачи: **часть сущностей Foundry не имеет места
назначения** в текущей модели кампании.

| Foundry | Куда | Потери |
|---|---|---|
| Scene | `maps.world` | слои, освещение, двери, погода |
| Scene (карта боя) | `maps.battle` | то же |
| Tokens на сцене | `tokens[]` | виджеты, размер, аудито |
| Actor | `sheet` | поля вне модели D&D 5e 2014 |
| JournalEntry | **новое** `adventure.notes[]` | — |
| Item | **новое** `adventure.items[]` | — |
| RollTable | **новое** `adventure.tables[]` | макросы не переносятся |
| Macro | — | не переносится |

### Требует решения владельца проекта

1. **Куда класть сцены.** В модели ровно три слота карт. Варианты: первая сцена
   занимает свободный слот, остальные требуют явного выбора; либо импортируются
   только фоновые карты без слоёв.
2. **Акторы.** Маппинг 30+ полей `actor.system` на лист вручную. Предлагаю в
   первой версии импортировать акт-карту и базовое имя, а лист предлагать
   заполнить вручную — автоматический маппинг полей даст тихую порчу данных.
3. **Актор без сцены.** Если у актора нет токена, появляется ли он в списке
   участников? Лист участника и NPC в игре — разные сущности, сейчас нет места
   для NPC.
4. **Формат кампании.** Появление секции `adventure` поднимает
   `CAMPAIGN_FORMAT_VERSION` с 1 до 2. Нужна ли миграция, или достаточно
   читать старые кампании как `adventure: null`?

## 10. Сохранение и отчёт

Запись — одним изменением кампании через существующий `CampaignStore`,
с последующим автосохранением как обычно. Частичный импорт запрещён: либо
применилось всё выбранное, либо ничего.

Отчёт содержит: что импортировано, что пропущено и почему, какие потери
при маппинге, сколько заняли карты и файлы.

## 11. Безопасность

- никакого исполнения кода из импортируемых файлов;
- только чтение из выбранного пользователем пути, без обхода каталогов;
- сетевой источник требует явного подтверждения перед загрузкой;
- проверка сигнатуры изображений обязательна, MIME не доверяем;
- размер файла проверяется до полного чтения в память.

## 12. IPC

В `preload.js` добавляются четыре метода; в main-процессе — четыре обработчика.

```js
inspectAdventure(filePath)   // -> ImportPreview
importAdventure(filePath, options) // -> ImportResult
```

Плюс два служебных, если решение по п.9 потребует:

```js
readAdventureFile()   // открыть диалог выбора файла
```

Ключевой момент: `filePath` приходит из renderer, поэтому main обязан
перепроверять, что путь существует, что это файл и что его расширение входит в
белый список. Иначе renderer сможет уговорить main прочитать что угодно.

## 13. Что не делаем в первой версии

- Roll20, D&D Beyond, PDF, собственные архивы — только точки расширения;
- чтение compendium-паков (этап 3);
- обратная выгрузка в Foundry;
- автообновление импортированного приключения.

## 14. Разбивка на этапы

**Этап 1.** Ядро конвейера + адаптеры JSON и ZIP + маппинг сцен в карты +
журнал в `adventure.notes` + интерфейс выбора. Без новых зависимостей.

**Этап 2.** Импорт актора с предпросмотром распознанных полей и диалогом
конфликтов при повторном импорте.

**Этап 3.** Compendium-паки через `classic-level`. Первым делом — снятие
зависимости от `@foundryvtt/foundryvtt-cli` в пользу прямой работы с NeDB,
если её API не даёт нужного.

## 15. Критерии приёмки

Этап считается закрытым, если:

- импорт не меняет ни одного существующего поля кампании вне своей секции;
- повторный импорт того же файла не плодит дубликаты;
- нераспознанное не приводит к падению — попадает в отчёт;
- файл размером больше лимита отклоняется до чтения целиком;
- карта из импорта проходит ту же проверку подписи, что и загруженная вручную;
- в тестах есть сценарий на каждый тип сущности из таблицы п.9;
- всё это проходит `node test/integration.js` и `node test/packaged-smoke.js`.

## 16. Что нужно проверить на реальном файле

Документация Foundry недоступна из этой среды, поэтому структура данных ниже —
**непроверенные предположения**. До начала этапа 2 нужно снять дамп:

1. JSON-экспорт Adventure — корневой объект, ключи, где лежат сцены и акты.
2. `packs/<name>/*.json` внутри ZIP модуля — совпадает ли структура с экспортом.
3. `actor.system` для системы dnd5e — точные имена полей.
4. `rolltable.results[]` — формат результата, где встречаются макросы.

Дамп снимается один раз, оформляется в `test/fixtures/` и становится основой
адаптера. Без него адаптер придётся писать вслепую.

## 17. Итог

Главный риск задачи — не чтение форматов, а то, что модель кампании рассчитана
на игроков, а Foundry-приключение полно NPC, журналов и таблиц, для которых
места нет. Решения из п.9 стоит принять до написания кода.
